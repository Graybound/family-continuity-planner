# Architecture

Family Continuity Planner is a static, single-page app written in TypeScript with no runtime dependencies. It builds into one self-contained HTML file that runs from disk, a USB drive, a NAS, or any static host.

## Technology choices

| Choice | Why |
|---|---|
| **TypeScript, no UI framework** | The app is a few forms, lists, and dialogs. A framework would add a runtime dependency, a larger bundle, and a learning step for contributors without solving a real problem. Strict types catch most mistakes in data handling, which is where bugs would hurt most. |
| **A 60-line DOM helper** ([src/ui/dom.ts](src/ui/dom.ts)) | `h(tag, props, ...children)` builds elements with text nodes only. This makes HTML injection structurally impossible and replaces v1's template strings plus `innerHTML`. |
| **Vite** | Fast dev server and a well-supported production build. |
| **vite-plugin-singlefile** | Inlines all JavaScript and CSS into `index.html`, so the release is one file that works over `file://` (where browsers block ES module files loaded separately). |
| **Vitest** | Unit tests for all data logic, sharing Vite's TypeScript handling. |
| **Playwright + axe-core** | Browser tests run against the real built file over `file://`, plus automated accessibility checks. |
| **ESLint (typescript-eslint)** | Includes project rules that forbid `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval`, and `fetch` in app code. |

If the UI grows substantially (many more interactive screens), a small library such as Preact or Lit could be reconsidered. That should be a deliberate decision recorded here.

## Source layout

```

  index.html            page shell, theme bootstrap script
  main.ts               entry point
  core/                 pure logic, no DOM, fully unit tested
    sections.ts         section (module) and field definitions, area labels, checklist groups
    plan.ts             schema v2 types, blank plan, default Start Here text
    normalize.ts        validation: builds a fresh, typed Plan from any input
    migrate.ts          schema detection and migrations (v1 to v2)
    backup.ts           safe JSON parse, import preview, export serialization
    storage.ts          localStorage load/save with damaged-data recovery
    readiness.ts        module status and readiness levels
    audit.ts            continuity review rules
    recommend.ts        assessment to tiered section recommendations
    search.ts           search across records, checklist, messages
    sample.ts           fictional sample plan
    ids.ts, dates.ts    helpers
  ui/                   DOM code
    store.ts            the single plan object, UI state, mutate(), navigation
    app.ts              shell: nav, top bar, banners, routing, shortcuts, mobile menu
    dom.ts              h() builder, focus capture and restore
    dialogs.ts          modal helper, confirm, record, checklist, message forms
    backupFlow.ts       export, restore preview, sample data, erase
    print.ts            printed packet builder
    printDialog.ts, searchDialog.ts, theme.ts, toast.ts
    views/              one file per screen
  styles/app.css, print.css
tests/
  unit/                 Vitest, Node environment
  e2e/                  Playwright against dist/index.html
  fixtures/             legacy-v1-export.json generated by the real v1 app
scripts/                post-build CSP, release packaging, privacy scan, screenshots
legacy/                 the recovered original build, unchanged
```

The rule of thumb: anything that decides something about data lives in `core/` and has unit tests. `ui/` only displays and collects.

## State management

`ui/store.ts` holds one `Plan` object and a small `UiState` (current view, privacy mode, filters, banners). Every change goes through `mutate(fn, options)`, which applies the change, updates `info.updatedAt`, saves to storage, shows an optional confirmation, and re-renders. There is no reactive framework: rendering rebuilds the current view from state.

Re-rendering everything is simple and fast at this size. To keep keyboard and screen-reader users oriented, interactive elements carry a `data-focus-key`; focus and caret position are captured before a render and restored after. After navigation, focus moves to the new view's heading.

## Storage

See [PRIVACY.md](PRIVACY.md) for the user-facing summary. Keys:

| Key | Contents |
|---|---|
| `familyContinuityPlanner.v2` | Current plan (schema 2 JSON) |
| `familyContinuityPlanner.v1` | v1 plan. Read only when the v2 key is absent. Never written |
| `familyContinuityPlanner.recovery.<ISO time>` | Text that failed to load, preserved before anything else is saved |
| `familyContinuityPlanner.theme` | `light` or `dark` |

`loadPlan()` returns one of `empty`, `ok`, `migrated-legacy`, `damaged`, or `unavailable`, and the app shows a matching banner. `savePlan()` reports quota and other failures as user-visible errors. A `storage` event from another tab shows a banner asking the user to reload.

## Data schema (version 2)

Full field-by-field reference: [docs/backup-format.md](docs/backup-format.md).

```ts
interface Plan {
  schema: 'family-continuity-planner';
  schemaVersion: 2;
  info: { planName, region,  // "meta" in v1; renamed so v1 rejects v2 files
          trustedContact, createdAt, updatedAt, lastReviewedAt, lastExportedAt, isSample };
  preferences: { privacyDefault, includePrivateInPrint };
  startHere: { mode: 'default' | 'custom'; customText };
  messages: { id, audience, title, body }[];
  records: Record<SectionId, { id, ...fields: string }[]>;
  checklist: { id, group, title, note, due, done }[];
  modules: Partial<Record<SectionId, 'completed' | 'review-later' | 'not-applicable'>>;
  assessment: { areas: Partial<Record<AreaId, Handler>>; risks: RiskId[]; completedAt };
  audit: { dismissed: string[]; deferred: Record<findingId, 'YYYY-MM-DD'> };
  activity: { id, text, at }[];
}
```

How the spec's concepts map onto it: life domains and modules are **sections**; responsibilities, trusted helpers, service providers, instructions, and document locations are records in the matching sections (`responsibilities`, `contacts`, `documents`, and so on); module status is `modules`; readiness is computed, never stored; audit findings are computed, and only the user's dismiss and defer choices are stored.

All record values are strings. That keeps validation simple and means nothing in a plan can be interpreted as code.

## Validation, backup format, and migrations

Every input, whether from storage or a file, takes the same path:

1. `safeJsonParse` parses JSON with a reviver that drops `__proto__`, `constructor`, and `prototype`. Files over 10 MB are rejected first.
2. `detectVersion` identifies v2 (by `schema` marker), v1 (by shape), a newer schema (rejected with a clear message), or something else (rejected).
3. `migrateToCurrent` applies registered migrations in order (`MIGRATIONS[1]` turns v1 into v2).
4. `normalizePlan` builds a **new** object containing only known keys, coerces and length-limits strings, strips control characters, validates dates and enum values, replaces unsafe or duplicate IDs, and collects human-readable warnings.

To add schema version 3: write `migrateV2toV3`, register it, bump `SCHEMA_VERSION`, commit a fixture file produced by version 2, add tests, and document the change. Never edit an existing migration.

## Readiness and audit

Deterministic pure functions in `core/readiness.ts` and `core/audit.ts`. Rules and thresholds are listed in [docs/readiness-and-audit.md](docs/readiness-and-audit.md) and covered by unit tests. No AI service is involved; any future AI feature would be optional and separate from this core.

## Printing

`ui/print.ts` builds a plain document into `#print-packet`, which only print CSS shows. `@page { size: letter }` with page breaks after the cover and Start Here, avoided breaks inside records and after headings, and `pre-wrap` text for long notes. The packet is a list of parts (`PACKET_ORDER`):

cover, start-here, immediate (emergency plans and the First 24 hours checklist), contacts, responsibilities, people, health, home, accounts, documents, notes, remaining checklists, messages (each on a new page).

Audience-specific packets (executor, caregiver, technology helper, messages only) are planned: each would be a different list of parts plus optional field filtering. They are not implemented.

## Security boundaries

- No network access: no `fetch`, enforced by lint and by `connect-src 'none'`.
- No HTML parsing of user data: enforced by the DOM helper, lint rules, and CSP.
- Imported files are data only and pass through the validation pipeline above.
- Destructive actions (delete, restore, load sample over a real plan, erase) require confirmation; the last three require an explicit acknowledgement checkbox.

## Testing strategy

- **Unit (Vitest):** backup round trips, v1 compatibility using the real fixture, malicious and malformed files, storage recovery, readiness levels, audit rules, recommendations, search.
- **Browser (Playwright, built file over `file://`):** every test fails if any network request or console error occurs. Covers CRUD, checklist, search, theme persistence, privacy mode, legacy storage upgrade, damaged storage recovery, export/restore with preview, invalid files, XSS attempts, print packet content and print media, keyboard-only workflows, mobile menu, offline operation, sample data, erase, and axe checks of every view in light and dark themes.

## Offline distribution and the single-file build

`npm run build` runs type checks, builds `dist/index.html` with everything inlined, then `scripts/post-build.mjs` adds the hash-based CSP and fails if any external URL appears. `npm run release` writes `release/Family-Continuity-Planner-vX.Y.Z.html`, a `.zip` with the app, a plain-text START-HERE guide, the license, and sample backups, and `SHA256SUMS.txt`. The zip is written with Node's built-in zlib and fixed timestamps.
